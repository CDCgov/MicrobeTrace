MicrobeTrace GA4 Initial Analytics Plan

Focused event taxonomy, complete export coverage, and privacy-safe implementation

Updated: September 2, 2026 Scope: MicrobeTrace web application Status: Initial code implementation complete; GA4 provisioning and live validation pending
Approved initial release

Use manual page views identified only by an allowlisted page_title and six privacy-safe custom event families: application entry, file import, analysis launch, focused feature-use actions, exports, and redirects to MicrobeTrace Classic. Imports and exports share source-view, file-type, and file-format dimensions. Export tracking covers every current export path. GA4 automatic collection is constrained so it cannot bypass the same privacy rules.

Current implementation status

The application instrumentation, environment routing, URL sanitization, and focused automated regressions are implemented. Remaining operator work is to register the five event-scoped custom dimensions in both GA4 properties, exercise controlled traffic against the dedicated test property, and complete analytics and privacy review before production rollout.

1. Executive summary

This first release is intentionally focused on a small set of product questions and a privacy-safe implementation. It measures application entry methods, view opens, broad file workflows, selected analysis features, complete export activity, configuration and map-file use, and redirects to MicrobeTrace Classic without collecting file contents or user-entered values.

This release limits MicrobeTrace application telemetry to seven MicrobeTrace-defined event families. The existing page_view event remains, and six custom events are included: app_entry, file_import, analysis_launch, analysis_action, export_action, and classic_redirect. GA4 may still generate standard automatic events such as session_start, first_visit, and user_engagement; those remain subject to GA4 default collection behavior and the property-level privacy controls in this plan.

Questions this release will answer

  • Which MicrobeTrace views are opened?
  • Did an application load begin normally, through a partner handoff, or through a URL import?
  • Which hostnames are running deployed copies of MicrobeTrace?
  • Which broad file types and formats are imported, and do those imports succeed or fail?
  • How often do users start a new analysis or update an existing analysis?
  • Which network filtering settings are used, and is timeline mode used?
  • Are MicrobeTrace style files, node color-assignment files, custom maps, or floorplans imported successfully?
  • How often do users choose to open MicrobeTrace Classic, and from which entry point?
  • Which view or workspace area is exported, what kind of artifact is produced, and in what format?

Explicitly deferred

  • Search usage, 2D node grouping, node and link selections, individual manual styling controls, and specialized per-view controls.
  • Performance timings, retries, recovery sequences, detailed error codes, and runtime diagnostics.
  • Exact data, cluster, selection, and result counts.
  • release_version. It is a useful future diagnostic dimension but is not required to answer the initial product questions.
  • Admin API provisioning, a large JSON event catalog, and catalog-specific CI automation.

2. Event model and privacy contract

All MicrobeTrace-defined application telemetry passes through the existing AnalyticsService. Components do not call window.gtag directly. The service exposes typed helpers, validates event and parameter values against fixed allowlists, and does nothing whenever analytics is disabled or gtag is unavailable. GA4 standard automatic events are outside this service and therefore must be constrained through the approved tag, stream, and property settings below.

Never send to GA4

  • Filenames, file contents, uploaded field names, search text, filter values, group labels, or tooltip values.
  • Node IDs, link IDs, sequences, copied identifiers, session contents, or patient attributes.
  • Raw exception messages, stack traces, browser rejection payloads, or console output.
  • Latitude, longitude, ZIP codes, floorplan coordinates, or other precise locations.
  • Exact dataset, cluster, selection, search-result, or other potentially sensitive counts.
  • User IDs, advertising identifiers, or values used for remarketing or personalization.

A normal GA4 web implementation still collects standard session, approximate-location, browser/device, and first-party client-ID information. Environment routing

All non-local deployed copies use the production measurement ID, including the CDC GitHub Pages deployment, partner-hosted open-source deployments, and handoff sessions. The GA4 Hostname dimension and sanitized base page_location provide deployment-level reporting without adding a custom parameter, while page_title identifies the newly opened view. The Google tag’s default URL context is always the deployment base URL with its query and fragment removed; any initial referrer is reduced to its origin. A developer may deliberately change analyticsDisabledForLocalHost for local testing; this routes local traffic only to the dedicated test destination, never to the production property.

3.1 Application-entry and view-open events

Exactly one app_entry event is emitted per loaded MicrobeTrace application instance. It contains only the allowlisted action; the Google tag supplies the sanitized deployment-base location and, when available, origin-only referrer context.

actionTrigger
standardThe application loads without a pending partner handoff or url query input.
handoffThe application loads with a pending partner handoff. This classification takes precedence if a URL input is also present.
url_importThe application loads with a url query input and no pending partner handoff.

The event classifies how the application was entered; it does not assert that a handoff, URL retrieval, file processing, or later analysis launch succeeded. 3.5 Export result semantics

  • result=success: MicrobeTrace generated the artifact and invoked the browser download mechanism.
  • result=fail: an observable generation or download-initiation error occurred before that point.
  • The browser does not reveal whether a user ultimately accepted, renamed, canceled, or deleted the downloaded file. The analytics plan makes no claim about those outcomes and does not emit canceled for exports.

4. Implementation specification and status

4.1 Central analytics service

  • trackView is the sole page-view mechanism. The Google tag configuration uses send_page_view=false, and Enhanced Measurement history-change page views remain off.
  • Send only the allowlisted page_title from each manual page_view. Do not add view names or virtual paths to page_location or page_referrer; those fields use the sanitized deployment-level context configured by the Google tag.
  • Typed helpers implement app_entry, file_import, analysis_launch, analysis_action, export_action, and classic_redirect.
  • TypeScript union types and constant sets define every event and parameter value in this document, including result=success, result=fail, and observable result=canceled.
  • Only typed helper methods can emit MicrobeTrace events. Each helper rejects non-allowlisted value combinations and never passes arbitrary component objects to gtag.
  • Every non-local hostname routes to the production measurement ID, including cdcgov.github.io, partner deployments, and handoff flows. A narrow local-development denylist covers localhost, loopback addresses, and file URLs; missing-gtag cases remain suppressed.
  • The Google tag is configured with a query- and fragment-free deployment base URL before any events can be sent. Raw window.location.href is never used as analytics context. If an initial browser referrer exists, only its origin is sent.
  • Deliberate local testing is permitted only when the bootstrap is configured for the dedicated non-production measurement ID. The local-test toggle never enables the production measurement ID on localhost, 127.0.0.1, or ::1.

4.2 Workflow instrumentation

  • Application entry: classify the initial load before handoff query cleanup and emit app_entry once with action=standard, action=handoff, or action=url_import. Do not forward the handoff ID, imported URL, partner identifier, query string, or fragment. The tag-level sanitized page context applies to this event just as it does to every other event.
  • File import: emit once per processFiles batch after all supported file-processing promises settle, and once per user-selected Workspace configuration or Map background file. Saved-session wrappers always report file_type=session. Normalize compressed-session helpers so the batch observes their actual completion result.
  • Analysis launch: record the requested mode at launch and emit the terminal result from the existing load-generation and rendered-network lifecycle. Clear pending state after result=success, result=fail, result=canceled, or replacement by a newer launch.
  • Analysis actions: use an in-memory "already tracked" set keyed by action. Emit each action at most once per loaded MicrobeTrace application instance from the committed handlers listed in Section 3.3. Do not send a separate feature category. Number and range inputs must emit after a committed value, not for every keystroke or slider frame. Emit threshold_stability_applied separately from a manual link_threshold change; emit nearest_neighbor only when that pruning mode is first enabled; and emit distance_metric only after a genuine user change rather than restoration or synchronization.
  • Timeline: emit action=timeline_mode once per loaded MicrobeTrace application instance when a user first activates or deliberately interacts with timeline mode. Do not track individual starts, pauses, range changes, speed changes, or resets.
  • Configuration and Map files: emit terminal file_import results for user-selected style files, color-assignment files, GeoJSON custom maps, and image floorplans. Internal configuration or Map state applied during session restoration must not emit a separate import event.
  • Classic: route all three current Classic entry points through a shared tracked-navigation helper. Emit classic_redirect with the allowlisted action before opening the new tab, without forwarding the target or Auspice URL.

4.3 Export instrumentation

  • The typed trackExport helper requires view_name, file_type, file_format, and result, matching the file_import parameter contract.
  • Shared export requests include source view and file type so central PNG/JPEG/WEBP/SVG completion paths report accurately.
  • Direct exporters emit at artifact-completion or caught-failure points without requiring a full exporter refactor.
  • Pass the format as a constant or selected allowlisted value. Never forward a filename or arbitrary MIME string.
  • Treat Section 3.4 as the acceptance checklist. Future export code must add an allowlisted matrix entry and automated test.

4.4 GA4 custom definitions

The six custom event names are sent directly by MicrobeTrace and do not need to be created in the GA4 interface. Register the same five event-scoped custom dimensions in the production property and the dedicated non-production test property so their parameter values are available in standard reports and Explorations. No custom metrics are needed because GA4 already reports event counts. page_title, page_location, page_referrer, Event name, and Hostname are built-in dimensions and must not be registered as custom definitions.

Event parameterGA4 display nameDescription
resultResultSuccess, failure, or observable cancellation.
actionActionAllowlisted application entry method, committed analysis action, or Classic entry point within an event family.
view_nameView nameAllowlisted source view or workspace area for a file import or export.
file_typeFile typeAllowlisted broad file class shared by imports and exports.
file_formatFile formatAllowlisted normalized input or output format.

Provisioning still required: create these five definitions manually in each GA4 property with Event scope and the exact case-sensitive event parameter names above. The new file_type and file_format definitions replace data_type, export_category, and export_format for new events, while feature_name is no longer sent. Old definitions may be archived after historical-reporting needs are considered. Definitions are property-level, so configuring the test property does not configure production. An Admin API provisioner remains deferred until the number of definitions or environments makes manual setup materially burdensome.

4.5 GA4 property and stream configuration

  • A dedicated non-production GA4 property is used for controlled local and QA testing. Its web stream has its own measurement ID and the same privacy settings as production.
  • Keep every setting in Section 2 aligned across the production and non-production properties before sending validation traffic.
  • Record the local-development denylist, measurement IDs, URL-sanitization behavior, Enhanced Measurement state, privacy settings, and retention choices in the deployment checklist.
  • Do not mark events as key events, create audiences, link advertising products, or enable user-provided data as part of this initial release.

Initial reports should answer only the approved product questions below. Counts from analysis_action represent feature adoption within loaded MicrobeTrace application instances, not total interaction frequency, unique people, or uses per GA4 session.

Controlled validation

  • First use the dedicated test property, GA4 DebugView, and browser network inspection to verify event names and allowlisted values.
  • Run import, launch, core-analysis, configuration-file, Classic redirect, session-save/restore, and complete-export acceptance paths with non-sensitive fixtures.
  • Verify that no Enhanced Measurement event appears and that one view open produces one manual page_view.
  • Review payloads and property settings with the analytics and privacy owners before production rollout.
  • Compare event totals with deterministic automated journeys before using the data for product decisions.
