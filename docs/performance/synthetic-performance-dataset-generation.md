# Synthetic Performance Dataset Generation

This document describes how the committed synthetic performance fixtures are generated so bioinformaticians can evaluate whether they are appropriate stand-ins for real MicrobeTrace workloads.

The generated fixtures live under `cypress/fixtures/performance/` and are produced by:

```bash
node scripts/generate-performance-fixtures.js
```

The generator is deterministic. It uses a seeded linear congruential pseudo-random number generator, so rerunning the script should recreate the same files for the same script inputs.

This document covers the performance fixtures generated by `scripts/generate-performance-fixtures.js`. It does not cover every small Cypress fixture in `cypress/fixtures/`, such as small oracle or journey fixtures.

## Summary

| Fixture family | Files | Purpose | Biological realism |
| --- | --- | --- | --- |
| Generated graph CSVs | `average-graph-*`, `large-graph-*`, `stress-graph-*` | CSV parsing, graph merge, threshold visibility, Cytoscape rendering, 2D interactions | Not biological; graph-shape workload only |
| Generated clustered FASTA | `average-sequences.fasta`, `large-sequences.fasta`, `expanded-large-sequences-1000.fasta`, `stress-sequences-2000.fasta` | FASTA parsing, SNP distance computation, sequence-derived links, Alignment readiness | Clustered SNP workload, not pathogen evolution |
| Generated clustered Newick | `average-newick-500.nwk`, `large-newick-1000.nwk`, `stress-newick-2000.nwk` | Newick parsing, patristic preprocessing, thresholded edge generation, threshold re-query | Artificial branch-length workload, not inferred phylogeny |

## Generated Graph CSV Fixtures

Generated files:

| Tier | Node file | Link file | Nodes | Links | ID prefix |
| --- | --- | --- | ---: | ---: | --- |
| Average | `average-graph-nodes.csv` | `average-graph-links.csv` | 1,600 | 3,200 | `P` |
| Large | `large-graph-nodes.csv` | `large-graph-links.csv` | 5,000 | 10,000 | `LG` |
| Stress | `stress-graph-nodes.csv` | `stress-graph-links.csv` | 10,000 | 25,000 | `SG` |

Node generation:

- Each node has `_id`, `subtype`, and `Diag date`.
- IDs are deterministic and sequential, such as `P0001`, `LG00001`, or `SG00001`.
- `subtype` cycles through `A` to `H`.
- `Diag date` cycles through month/day combinations in 2024.

Link generation:

- The generator first adds a ring backbone: node `i` links to node `i + 1`, with the final node linking back to the first.
- Ring-link distances cycle from 4 to 11.
- It then adds deterministic pseudo-random links until the target link count is reached.
- Random links use an offset between 2 and 97 nodes from the source index.
- Random-link distances are integers from 6 to 12.
- Duplicate undirected pairs and self-links are skipped.

How these are used:

- Performance specs launch them with SNP metric and threshold `16`.
- Because every generated graph distance is below `16`, all committed graph links are visible at launch.
- These fixtures exercise graph ingestion and rendering paths, not sequence or phylogenetic inference paths.

Bioinformatics assessment notes:

- These are not epidemiologic or molecular simulations.
- They do not model realistic contact-network degree distributions, superspreading, sampling bias, facility outbreaks, geography, or metadata correlations.
- They are useful as deterministic graph-size workloads.
- If real user graphs have much heavier-tailed degree distributions, many isolates, or different visible-link densities, the generator should be adjusted or supplemented.

## Generated Clustered FASTA Fixtures

Generated files:

| Tier | File | Sequences | Clusters | Samples per cluster | Sequence length | SNP threshold | Expected visible links |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Average | `average-sequences.fasta` | 120 | 8 | 15 | 2,400 | 16 | 840 |
| Large | `large-sequences.fasta` | 300 | 15 | 20 | 1,800 | 16 | 2,850 |
| Expanded large | `expanded-large-sequences-1000.fasta` | 1,000 | 25 | 40 | 1,800 | 16 | 19,500 |
| Stress | `stress-sequences-2000.fasta` | 2,000 | 40 | 50 | 1,800 | 16 | 49,000 |

Sequence generation:

- The generator creates one deterministic random reference sequence using `a`, `c`, `g`, and `t`.
- It divides records into fixed clusters.
- Each cluster receives 12 unique signature SNP positions.
- Cluster signature positions are globally blocked so two clusters do not reuse the same signature position.
- Each cluster reference is made by mutating the shared reference at that cluster's signature positions.
- Each sample copies its cluster reference and receives 4 to 6 additional sample-level SNPs.
- Sample-level SNP positions are chosen outside the cluster-signature positions.
- Mutations are deterministic base rotations through `a/c/g/t`, not a probabilistic substitution model.
- FASTA records are written with deterministic IDs such as `SEQ0001` and `LSEQ0001`.

Validation built into the generator:

- Pairwise SNP distances are computed for all records.
- Every within-cluster pair must be at or below threshold `16`.
- Every cross-cluster pair must be above threshold `16`.
- The visible-link count must exactly match the expected within-cluster pair count.

Expected counts:

- Average: 8 clusters x `15 choose 2` = 840 within-cluster visible links.
- Large: 15 clusters x `20 choose 2` = 2,850 within-cluster visible links.
- Expanded large: 25 clusters x `40 choose 2` = 19,500 within-cluster visible links.
- Stress: 40 clusters x `50 choose 2` = 49,000 within-cluster visible links.

How these are used:

- Performance specs launch them as FASTA with SNP metric and threshold `16`.
- They measure FASTA parsing, sequence storage, SNP distance computation, link generation, 2D readiness, Alignment readiness, and 2D interaction responsiveness.

Bioinformatics assessment notes:

- These are not realistic pathogen-evolution simulations.
- They do not model a phylogeny, dated transmission tree, molecular clock, substitution model, transition/transversion bias, codon constraints, selection, recombination, indels, ambiguous bases, missing regions, sequencing error, lineage assignment, or sampling dates.
- The current design intentionally creates clean, threshold-separated clusters so performance assertions can predict exact link counts.
- If bioinformaticians want these to be more realistic, the next version should be generated from a dated tree or transmission tree with a real substitution model and controlled missingness/error.

## Generated Clustered Newick Fixtures

Generated files:

| Tier | File | Leaves | Clusters | Leaves per cluster | Initial threshold | Initial visible links | Re-query threshold | Re-query visible links |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Average | `average-newick-500.nwk` | 500 | 10 | 50 | 0.003 | 3,000 | 0.006 | 12,250 |
| Large | `large-newick-1000.nwk` | 1,000 | 20 | 50 | 0.003 | 6,000 | Not asserted in large baseline | Not asserted |
| Stress | `stress-newick-2000.nwk` | 2,000 | 40 | 50 | 0.003 | 12,000 | 0.006 | 49,000 |

Tree generation:

- The generator creates a root containing multiple cluster subtrees.
- Each cluster has 50 leaf nodes.
- Leaves in the first half of each cluster get terminal branch length `0.0010`.
- Leaves in the second half of each cluster get terminal branch length `0.0025`.
- Each cluster subtree attaches to the root with branch length `0.0500`.
- Leaf IDs are deterministic, such as `NWK0001`, `LNWK0001`, or `SNWK0001`.

Why the expected link counts are deterministic:

- At threshold `0.003`, only pairs among the first 25 leaves within each cluster are visible.
- Each cluster therefore emits `25 choose 2` = 300 visible links.
- Average: 10 clusters x 300 = 3,000 visible links.
- Large: 20 clusters x 300 = 6,000 visible links.
- Stress: 40 clusters x 300 = 12,000 visible links.
- At threshold `0.006`, all pairs within a 50-leaf cluster are visible because the largest within-cluster pair distance is `0.0025 + 0.0025 = 0.005`.
- Average re-query: 10 clusters x `50 choose 2` = 12,250 visible links.
- Stress re-query: 40 clusters x `50 choose 2` = 49,000 visible links.
- Cross-cluster pairs remain far above those thresholds because each cluster has a `0.0500` branch to the root.

How these are used:

- Performance specs launch them as Newick with TN93/patristic threshold `0.003`.
- The average and stress specs also change the threshold to `0.006` to verify cached tree re-query behavior.
- These are the main fixtures for measuring Newick parsing, patristic preprocessing, thresholded edge generation, and downstream 2D/Phylogenetic Tree readiness.

Bioinformatics assessment notes:

- These are artificial threshold workloads, not inferred phylogenies.
- They do not model realistic tree imbalance, within-cluster topology, lineage structure, temporal sampling, polytomy resolution, branch-length uncertainty, or realistic branch-length distributions.
- They intentionally create simple cluster boundaries and predictable patristic link counts.
- Bioinformaticians should treat them as algorithmic stress tests for patristic edge generation.
- A more realistic Newick fixture should include skewed topology, realistic branch-length ranges, zero or near-zero branches if common, and representative label formats.

## Performance Fixtures Not Generated by the Synthetic Generator

Some committed performance fixtures are not produced by `scripts/generate-performance-fixtures.js` and should be reviewed separately.

`problem_10k.csv`:

- Used by `problem-10k-node-only.perf.cy.ts`.
- It is a 10,253-row node-only CSV with many metadata columns and no links.
- It is documented in `docs/performance/problem-10k-node-only-performance.md`.
- It is not a sequence or phylogenetic simulation.
- It is used to test node-only ingestion, metadata-heavy table state, no-link 2D rendering, and grouping behavior.

`stress-tree.nwk`:

- Committed under `cypress/fixtures/performance/`.
- It is not generated by `scripts/generate-performance-fixtures.js`.
- It appears to be a real or real-like large Newick tree with named samples and many small branch lengths.
- It should not be described as one of the deterministic synthetic generated fixtures unless a provenance note is added.

`performance/dunes/*`:

- Optional outputs from `scripts/generate-dunes-performance-fixtures.js`.
- They are simple FASTA-only simulated sequence fixtures generated by DUNES from a source FASTA.
- They are not produced by the deterministic synthetic generator and should be regenerated with their matching summary JSON.
- See `dunes-performance-fixture-generation.md`.

`real-samples.example.json`:

- This is a configuration template for opt-in real sample scenarios.
- Real samples are intended to calibrate generated fixtures and validate real file shapes.
- They are not part of the deterministic synthetic baseline.

## What Reviewers Should Assess

Bioinformaticians reviewing these fixtures should focus on whether the synthetic shapes exercise realistic performance risks, not whether they are biologically complete.

Useful review questions:

- Are the average and large sequence counts realistic for current MicrobeTrace users?
- Are the selected SNP and patristic thresholds representative?
- Are the expected visible-link densities too sparse or too dense compared with real workflows?
- Do real sequence datasets often include ambiguous bases, gaps, masked regions, or missing sequence blocks that these fixtures omit?
- Do real Newick trees include branch-length and topology features that the current generated trees miss?
- Are graph degree distributions and metadata fields representative enough for 2D, Sankey, Aggregate, and filtering performance?
- Should future generated fixtures model dates, locations, host/facility metadata, or lineage labels more realistically?

## Review-Driven Fixture Improvements

The current generator is a solid first-generation engineering benchmark. It is intentionally deterministic and intentionally simple. The next generation should keep those stable fixtures, then add supplementary fixtures that exercise realistic browser, metadata, and biological-input risks.

Graph fixture additions:

| Fixture shape | Why it matters |
| --- | --- |
| many isolates plus small clusters | common in surveillance data |
| one dominant component | tests giant-component rendering and layout |
| hub-heavy network | stresses selection, highlighting, and neighborhood expansion |
| dense local outbreak cluster | stresses edge rendering |
| metadata-heavy graph | tests table, filtering, coloring, grouping, Sankey, and Aggregate workflows |
| high-cardinality categories | stresses legends and group-by UI |
| threshold-gradient graph | tests predictable link visibility changes at 10%, 25%, 50%, 75%, and 100% |

FASTA fixture additions:

| Fixture shape | Why it matters |
| --- | --- |
| 2,500-5,000-sequence manual fixture | stresses worker time, memory, and rendering after link generation |
| ambiguous bases and gaps | reflects common sequence quality issues |
| masked or missing regions | reflects HIV and pathogen workflows with incomplete regions |
| near-threshold pairs | tests threshold stability |
| mixed sparse and dense clusters | creates more realistic graph output |
| duplicate IDs and non-IUPAC characters | validates error handling |

Newick fixture additions:

| Fixture shape | Why it matters |
| --- | --- |
| balanced tree | baseline topology |
| highly imbalanced tree | stresses traversal and cache behavior |
| polytomy-rich tree | reflects low-resolution inferred trees |
| zero-length branches | common with identical or unresolved sequences |
| tiny and near-threshold branch lengths | tests numeric precision |
| duplicate labels | validates upload errors |
| long or unusual sample names | tests parsing and rendering |
| mixed cluster sizes or one large clade | more realistic than fixed 50-leaf clusters |

The browser-based tier sizes in `performance-dataset-strategy-for-bioinformaticians.md` should guide which of these fixtures run in CI, nightly, pre-release, or manual stress mode. In particular, 10,000-leaf Newick and 5,000-sequence FASTA fixtures should be treated as manual stress tests, while 25,000+ Newick leaves or 10,000+ FASTA sequences are failure-mode tests for warning, throttling, or subsetting behavior. FASTA fixtures above the default 2,000,000 pairwise-link guardrail should validate warning/subsetting behavior unless a controlled manual run intentionally raises the guardrail.

Each new generated fixture should also have a manifest or documented shape summary with:

- fixture name and file names
- dataset type and tier
- sequence, leaf, node, and link counts as applicable
- metric and active thresholds
- expected visible links at those thresholds
- intended code paths
- known limitations
- whether the fixture is deterministic engineering data, real sample data, or bio-realistic simulation

Non-generated fixtures such as `problem_10k.csv` and `stress-tree.nwk` should keep separate provenance notes so they are not mistaken for deterministic synthetic fixtures.

## Recommended Next Generation Step

The current generated fixtures are adequate for deterministic performance baselines. They are not adequate as biological simulations.

For a more realistic pathogen-evolution fixture, generate sequences from a dated phylogeny or transmission tree using an explicit substitution model such as HKY or GTR, then add controlled sampling dates, metadata, ambiguous bases, masked regions, and optional sequencing error. Keep a deterministic seed and record expected pairwise distance and threshold-link counts so Cypress can still make exact assertions.
